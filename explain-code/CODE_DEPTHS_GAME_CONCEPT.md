# CODE DEPTHS — ดันเจี้ยนแห่งการเข้าใจ

> "AI ประกอบมนตร์ให้คุณได้ แต่คุณต้องเข้าใจมนตร์ก่อนร่าย"

ผู้เล่นนำโค้ดของตัวเองหรือโค้ดที่ AI เขียนเข้ามาในเกม โค้ดนั้นจะกลายเป็น "ร่องรอยพลัง" ที่สร้างดันเจี้ยน ผู้เล่นต้องอ่าน ทำนายผล อธิบาย และซ่อมโค้ดเพื่อเอาตัวรอด โดยเป้าหมายไม่ใช่พิสูจน์ว่าใครเขียนโค้ด แต่พิสูจน์ว่า **ผู้เล่นเข้าใจสิ่งที่กำลังนำไปใช้จริงหรือไม่**

หัวใจสำคัญคือ **โค้ดที่นำเข้าเป็นธีมของดันเจี้ยน ไม่ใช่หลักสูตรทั้งหมด**

---

## 1. Gameplay Loop ต่อหนึ่งรอบ

หนึ่งรอบใช้เวลาประมาณ **15–25 นาที**

1. **นำเข้าโค้ด**
   - วางโค้ดหรือเลือกไฟล์
   - เลือกเป้าหมาย เช่น "เข้าใจโค้ดนี้", "หาบั๊ก" หรือ "เตรียมอธิบายงาน"
   - ระบบวิเคราะห์โครงสร้าง เช่น ตัวแปร ลูป เงื่อนไข ฟังก์ชัน ข้อมูลที่ใช้ และจุดที่อาจเกิดข้อผิดพลาด

2. **สร้างดันเจี้ยนจากความรู้ 3 ชั้น**
   - **จากโค้ดจริง:** บรรทัดนี้ทำอะไร ค่าตัวแปรเปลี่ยนอย่างไร ผลลัพธ์คืออะไร
   - **จากพื้นฐานที่เกี่ยวข้อง:** แนวคิดที่ต้องรู้ก่อน ข้อเข้าใจผิดที่พบบ่อย และกรณีขอบเขต
   - **จากการประยุกต์:** โค้ดใหม่ที่ใช้แนวคิดเดียวกัน หรือโจทย์ที่เปลี่ยนความต้องการเล็กน้อย

3. **เลือกเส้นทางบนแผนที่**
   - ห้องต่อสู้ ห้องซ่อมของ ห้องทดสอบ ห้องเหตุการณ์ และห้องบอส
   - เส้นทางปลอดภัยให้รางวัลน้อย ส่วนเส้นทางยากให้ relic หรือข้อมูลพิเศษ

4. **ใช้ความเข้าใจโค้ดเปลี่ยนสถานะเกมจริง**
   - ทำนายผลถูก -> หลบการโจมตีและสะท้อนความเสียหาย
   - หาบั๊กเจอ -> ปิดกับดัก
   - อธิบายฟังก์ชันได้ -> ปลดล็อกเวทของฟังก์ชันนั้น
   - แก้โค้ดให้รองรับ edge case -> ซ่อมสะพานหรือเปิดทางลัด

5. **จบรอบด้วยบอสและรายงานความเข้าใจ**
   - ไม่ได้บอกแค่ว่าได้กี่คะแนน แต่บอกว่าผู้เล่น "ทำนายได้ อธิบายได้ ดีบั๊กได้ หรือประยุกต์ได้" ระดับใด

## 2. ตัวอย่างห้องและมอนสเตอร์

| ห้อง/มอนสเตอร์ | กิจกรรม | สิ่งที่วัด |
|---|---|---|
| **Trace Slime** | เรียงลำดับบรรทัดที่ทำงาน หรือเลือกค่าตัวแปรหลังลูปรอบที่ 2 | การอ่าน flow และ state |
| **Off-by-one Bat** | เลือก input ที่ทำให้ลูปหรือ index ผิดพลาด | ความเข้าใจ boundary |
| **Scope Wraith** | ระบุว่าตัวแปรตัวใดมองเห็นได้จากตรงไหน | scope และ lifetime |
| **Bug Mimic** | โค้ดดูเหมือนถูก แต่ล้มเหลวกับบาง input | การทดสอบและการหาบั๊ก |
| **Shrine of Why** | ตอบว่าทำไมต้องใช้โครงสร้างนี้ แทนที่จะตอบแค่ว่ามันทำอะไร | ความเข้าใจเชิงเหตุผล |
| **Refactor Forge** | เลือกหรือแก้โค้ดให้ตรงความต้องการใหม่ โดยเปลี่ยนให้น้อยที่สุด | การแก้ไขโดยรักษาพฤติกรรมเดิม |
| **Transfer Gate** | อ่านโค้ดที่ไม่เคยเห็น แต่ใช้ pattern เดียวกัน | การโอนย้ายความรู้ |

จุดสำคัญคือ **อย่าทำให้มอนสเตอร์เป็นเพียงภาพประกอบของข้อสอบ** เช่น ถ้าผู้เล่นหาบั๊กในเงื่อนไขไม่เจอ กับดักในห้องควรทำงานตามเงื่อนไขผิดนั้นจริงๆ ทำให้ผู้เล่นเห็นความเชื่อมโยงระหว่างโค้ดกับเหตุการณ์ในเกม

## 3. ระบบไม่ได้ถามเฉพาะโค้ดที่นำเข้า

ใช้ **Knowledge Graph** เป็นตัวกำหนดสิ่งที่ควรสอดแทรก โดยแต่ละแนวคิดเชื่อมกับ:

- ความรู้ที่ต้องมีก่อน (Prerequisites)
- ข้อเข้าใจผิดที่พบบ่อย (Misconceptions)
- รูปแบบการใช้งานอื่น (Idiomatic Patterns)
- Edge cases และวิธีทดสอบ
- หัวข้อต่อยอด เช่น ประสิทธิภาพ ความซับซ้อน หรือความปลอดภัย หากเกี่ยวข้อง

สัดส่วนเริ่มต้นของดันเจี้ยน:

- **40%** โค้ดของผู้เล่น
- **30%** พื้นฐานและความเข้าใจผิดที่เกี่ยวข้อง
- **30%** โค้ดใหม่หรือสถานการณ์ประยุกต์

สัดส่วนนี้ปรับตามผู้เล่นได้ หากอ่านโค้ดตัวเองได้แต่ประยุกต์ไม่ได้ รอบถัดไปควรเพิ่มห้อง Transfer ไม่ใช่สุ่มคำถามเดิมให้ยากขึ้นเพียงอย่างเดียว

### ตัวอย่าง

ผู้เล่นนำเข้าโค้ด:

```python
def average(xs):
    total = 0
    for x in xs:
        total += x
    return total / len(xs)
```

ดันเจี้ยนอาจประกอบด้วย:

1. **ห้อง Trace:** เมื่อ `xs = [2, 4, 6]` ค่า `total` เปลี่ยนอย่างไรในแต่ละรอบ
2. **ห้อง Concept:** `total` มีบทบาทเป็น accumulator อย่างไร และตัวแปรนี้มี scope แค่ไหน
3. **ห้อง Edge Case:** เกิดอะไรขึ้นเมื่อ `xs = []`
4. **ห้อง Transfer:** แสดงฟังก์ชันอื่นที่ใช้ pattern เดียวกัน แล้วให้ระบุตัวสะสมค่าและค่าเริ่มต้น
5. **บอส:** อธิบายสาเหตุของ `ZeroDivisionError` เลือกวิธีแก้ และเลือก test case ที่ควรใช้ตรวจว่าแก้สมบูรณ์
6. **เนื้อหาต่อยอดเมื่อพร้อม:** เพราะเหตุใดอัลกอริทึมนี้จึงใช้เวลาโดยประมาณ `O(n)`

ดังนั้น แม้ผู้เล่นจำคำตอบจากโค้ดเดิมได้ ก็ยังต้องเข้าใจแนวคิดพอที่จะใช้กับสถานการณ์ใหม่

## 4. บอส: "The Core" ตรวจความเข้าใจ 3 เฟส

บอสไม่ควรถามยาวๆ ครั้งเดียว แต่ไล่จากง่ายไปลึก:

### เฟสที่ 1: Predict — ทำนายก่อนรัน
ให้ input หนึ่งชุด แล้วถามผลลัพธ์ ลำดับการทำงาน หรือค่าของตัวแปรสำคัญ

### เฟสที่ 2: Explain — อธิบายเชิงสาเหตุ
ใช้คำถาม เช่น:
- ฟังก์ชันนี้รับอะไรและคืนอะไร?
- ทำไมต้องกำหนดค่าเริ่มต้นให้ `total`?
- ถ้าเปลี่ยนบรรทัดนี้ พฤติกรรมใดจะเปลี่ยน?
- input แบบใดที่โค้ดนี้ยังจัดการไม่ได้?

สำหรับผู้เรียนระดับต้น อาจมีโครงช่วยตอบ:
> "โค้ดนี้รับ ___ แล้วใช้ ___ เพื่อ ___ แต่ถ้า input เป็น ___ จะเกิด ___"

### เฟสที่ 3: Repair & Transfer
เปลี่ยน input หรือความต้องการเล็กน้อย แล้วให้ผู้เล่นแก้โค้ด เลือกแนวทาง หรืออธิบายวิธีแก้ พร้อมทดสอบกับกรณีใหม่

ถ้าตอบผิด เกมไม่ควรเฉลยทันที แต่แสดง **visual execution** เช่น ตารางค่าตัวแปรหรือการเดินทีละบรรทัด จากนั้นให้ลองคำถามใกล้เคียงที่เปลี่ยนค่า input เพื่อไม่ให้จำคำตอบ

## 5. ความเป็น Roguelite ที่เหมาะกับเกมการเรียนรู้

ใช้แบบ **Roguelite** มากกว่า roguelike เต็มรูปแบบ เพราะแม้รอบเกมจะรีเซ็ต แต่ความรู้ไม่ควรถูกลบ

- **สุ่มแผนที่และ encounters** จากโครงสร้างโค้ด จุดอ่อนของผู้เล่น และ knowledge graph
- **HP คือ Program Integrity** ลดเมื่อตอบผิดหรือใช้โค้ดโดยไม่ตรวจสอบ
- **Focus คือ resource สำหรับขอคำใบ้** เช่น ดูค่าตัวแปรหนึ่งรอบ หรือเปิด execution หนึ่งบรรทัด
- **Relic เป็นกลยุทธ์การเรียนรู้** เช่น Trace Table, Rubber Duck, Test Oracle ไม่ใช่แค่ไอเทมเพิ่มพลังโจมตี
- **เมื่อพ่าย ความรู้และ Codex ยังอยู่** แต่ build ของรอบนั้นหายไป
- **ปลดล็อก challenge modifiers** เช่น ไม่มีตัวเลือกให้, ใช้ input แปลกใหม่ หรืออธิบายด้วยเสียง แทนการเพิ่มสเตตัสจนเกมง่ายลง

การสุ่มไม่ควรหมายถึง "สุ่มข้อสอบมาใส่ห้อง" แต่ต้องสุ่มภายใต้เป้าหมายการเรียนรู้ที่ชัดเจน

## 6. วัดผลและจัดการเรื่องการใช้ AI อย่างไร

ไม่ควรพยายามตรวจว่า "โค้ดนี้ AI เขียนหรือไม่" เพราะตรวจได้ไม่น่าเชื่อถือ และไม่ใช่เป้าหมายหลัก ควรวัดพฤติกรรมที่พิสูจน์ความเข้าใจแทน โดยให้คะแนน 4 มิติ:

1. **Predict:** ทำนายผลและติดตาม state ได้
2. **Explain:** อธิบายจุดประสงค์และเหตุผลได้
3. **Debug:** หา input ที่ทำให้ผิด และซ่อมได้
4. **Transfer:** ใช้ความรู้กับโค้ดหรือปัญหาใหม่ได้

คำถามควรมี input ที่เปลี่ยนแปลงได้ มีคำถามตามว่า "ทำไม" และมีงานประยุกต์สั้นๆ ในเกม วิธีนี้ไม่ได้ป้องกันการโกงได้สมบูรณ์ แต่ทำให้การกดผ่านจากคำตอบของ AI อย่างเดียวสร้างหลักฐานความเข้าใจไม่ได้

สำหรับคำอธิบายแบบข้อความ AI สามารถช่วยประเมินตาม rubric ได้ แต่ไม่ควรใช้เป็นผู้ตัดสินเพียงฝ่ายเดียวในการให้เกรดสำคัญ ส่วนคำถามที่มีคำตอบตรงตัว เช่น output หรือค่าตัวแปร ควรตรวจด้วยการรันโค้ดใน sandbox และการทดสอบอัตโนมัติ

## 7. MVP ที่ทำได้จริงโดยไม่ต้องสร้างเกมใหญ่เกินไป

เริ่มจาก:

- รองรับ **Python** ก่อน และจำกัดเป็นฟังก์ชันหรือโค้ดขนาดเล็ก
- แผนที่แบบ node 2D (แนว Slay the Spire / FTL) และการต่อสู้แบบ turn-based
- ห้องประมาณ 6–8 ห้อง พร้อมบอส 1 แบบ
- แม่แบบกิจกรรม 5 อย่าง: trace, predict, spot-the-bug, edge-case test และ short explanation
- Knowledge graph เริ่มต้น เช่น variables, data types, conditionals, loops, functions, scope, lists, errors และ testing
- รายงานท้ายรอบว่า "จุดไหนอ่านได้แล้ว จุดไหนยังเดา และควรฝึกอะไรต่อ"
- สำหรับครู มี class heatmap ของ misconception เช่น "ส่วนใหญ่เข้าใจลูป แต่ยังจัดการ empty input ไม่ได้"

ตัวชี้วัดที่ควรใช้คือ **นักเรียนทำโจทย์ใหม่ที่คล้ายกันได้หรือไม่หลังผ่านไปหนึ่งวันหรือหนึ่งสัปดาห์** มากกว่าจำนวนด่านที่เคลียร์หรือคะแนนในเกม

สรุปสั้นๆ คือเกมนี้ไม่ได้ลงโทษนักเรียนที่ใช้ AI แต่เปลี่ยนเส้นทางจาก **"ได้โค้ดแล้วส่งงาน"** ให้กลายเป็น **"นำโค้ดเข้าดันเจี้ยน -> ทำนาย -> อธิบาย -> ซ่อม -> ประยุกต์ -> จึงได้ว่าเข้าใจจริง"**
